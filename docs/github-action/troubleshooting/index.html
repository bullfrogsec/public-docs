Troubleshooting

This guide helps you resolve common issues when using Bullfrog in your GitHub Actions workflows.

Reviewing Blocked Connections​

When connections are blocked or logged, you can view them in the workflow summary.

How to Access the Workflow Summary​

  1. Navigate to your workflow run in GitHub Actions
  2. Scroll to the bottom of the page
  3. Look for the "Workflow Summary" section
  4. Find "Bullfrog Network Report" or similar heading

What You'll See​

The summary includes:

  • Allowed Connections: Connections that matched your allow list
  • Blocked Connections: Connections that were blocked (in block mode)
  • Unallowed Connections: Connections that would be blocked (in audit mode)

Each entry shows:

  • Destination IP address and port
  • Domain name (if available)
  • Timestamp
  • Protocol (TCP/UDP)

Common Issues​

Issue: Workflow Fails with "Connection Refused"​

Symptoms:

Error: connect ECONNREFUSED
npm ERR! network request failed

Causes:

  • Required domain/IP not in allow list
  • DNS resolution blocked
  • Typo in allowed-domains configuration

Solutions:

  1. Run in audit mode first:
- uses: bullfrogsec/bullfrog@1831f79cce8ad602eef14d2163873f27081ebfb3 # v0.8.4
  with:
    egress-policy: audit

  1. Check the workflow summary to see what connections are being made

  2. Add missing domains/IPs to your allow list:

- uses: bullfrogsec/bullfrog@1831f79cce8ad602eef14d2163873f27081ebfb3 # v0.8.4
  with:
    egress-policy: block
    allowed-domains: |
      registry.npmjs.org
      # Add domains from audit log

Issue: DNS Resolution Fails​

Symptoms:

Error: getaddrinfo ENOTFOUND
Could not resolve host: example.com

Causes:

  • DNS policy set to allowed-domains-only but domain not in list
  • DNS servers blocked

Solutions:

  1. Add domain to allowed-domains:
allowed-domains: |
  example.com
  1. Or use dns-policy: any:
- uses: bullfrogsec/bullfrog@1831f79cce8ad602eef14d2163873f27081ebfb3 # v0.8.4
  with:
    egress-policy: block
    allowed-ips: |
      1.2.3.4
    dns-policy: any # Allow DNS for any domain

Issue: Wildcard Not Working​

Symptoms:

  • Added *.example.com but example.com still blocked
  • Subdomains still being blocked

Causes:

  • Wildcards don't match the base domain
  • Incorrect wildcard syntax

Solutions:

Add both base domain and wildcard:

allowed-domains: |
  example.com       # Base domain
  *.example.com     # Subdomains

Issue: Docker Pull Fails​

Symptoms:

Error response from daemon: Get https://registry-1.docker.io/v2/: net/http: request canceled

Causes:

  • Missing Docker-related domains
  • Only added docker.io but not CDN domains

Solution:

Add all Docker domains:

allowed-domains: |
  *.docker.com
  docker.io
  *.docker.io

See Docker Registry guide for details.

Issue: Bullfrog Not Running​

Symptoms:

  • No Bullfrog output in logs
  • Connections not being monitored

Causes:

  • Bullfrog not added as first step
  • Using unsupported runner (Windows/macOS)
  • Using container job

Solutions:

  1. Ensure Bullfrog is first step:
steps:
  - uses: bullfrogsec/bullfrog@1831f79cce8ad602eef14d2163873f27081ebfb3 # v0.8.4
  - uses: actions/checkout@v4 # Other steps after
  1. Verify runner OS:
runs-on: ubuntu-latest # ✅ Supported
# runs-on: windows-latest  # ❌ Not supported
  1. Check you're not using container jobs:
jobs:
  build:
    runs-on: ubuntu-latest
    # container: node:18  # ❌ Remove this

Issue: "Permission Denied" Errors​

Symptoms:

Error: EPERM: operation not permitted
sudo: command not found

Causes:

  • enable-sudo: false but workflow requires sudo

Solutions:

  1. Enable sudo (not recommended for security):
- uses: bullfrogsec/bullfrog@1831f79cce8ad602eef14d2163873f27081ebfb3 # v0.8.4
  with:
    enable-sudo: true
  1. Better: Refactor workflow to not need sudo

Issue: Connections to IP Addresses Blocked​

Symptoms:

  • Added domain to allow list
  • Connection still blocked because it goes to IP

Causes:

  • Application connects directly to IP
  • IP not in allowed-ips list

Solutions:

  1. Add the IP to allowed-ips:
allowed-ips: |
  1.2.3.4
  1. Or allow DNS for any domain:
allowed-domains: |
  example.com
dns-policy: any

Issue: Too Many Connections to Review​

Symptoms:

  • Workflow summary shows hundreds of connections
  • Difficult to identify which are necessary

Solutions:

  1. Start with minimal workflow:
steps:
  - uses: bullfrogsec/bullfrog@1831f79cce8ad602eef14d2163873f27081ebfb3 # v0.8.4
  - uses: actions/checkout@v4
  # Add steps one by one

  1. Add steps gradually and review connections after each

  2. Group by domain in your allow list:

allowed-domains: |
  # GitHub
  github.com
  *.github.com
  # npm
  registry.npmjs.org
  *.npmjs.org
  # Docker
  *.docker.com
  docker.io
  *.docker.io

Debugging Strategies​

Strategy 1: Incremental Lockdown​

  1. Start with audit mode (no blocking)
  2. Review all connections
  3. Create initial allow list
  4. Switch to block mode
  5. Fix any failures
  6. Gradually tighten allow list

Strategy 2: Test in Separate Branch​

  1. Create a test branch
  2. Add Bullfrog configuration
  3. Run workflow multiple times
  4. Refine configuration
  5. Merge when stable

Strategy 3: Parallel Workflows​

Run the same workflow with and without blocking:

jobs:
  build-protected:
    runs-on: ubuntu-latest
    steps:
      - uses: bullfrogsec/bullfrog@1831f79cce8ad602eef14d2163873f27081ebfb3 # v0.8.4
        with:
          egress-policy: block
          allowed-domains: |
            github.com
      # Rest of workflow

  build-audit:
    runs-on: ubuntu-latest
    steps:
      - uses: bullfrogsec/bullfrog@1831f79cce8ad602eef14d2163873f27081ebfb3 # v0.8.4
        with:
          egress-policy: audit
      # Same workflow steps

Compare the audit results to see what the protected version is blocking.

Getting Help​

Check Logs​

  1. Bullfrog Step Logs: Check the Bullfrog step output for errors
  2. Failing Step Logs: Check logs of steps that fail for connection errors
  3. Workflow Summary: Always check the summary for blocked/allowed connections

Enable Verbose Logging​

Add debugging to your workflow:

- name: Debug connection
  run: |
    set -x  # Enable bash debugging
    curl -v https://example.com  # Verbose curl output

Test Connectivity​

Add a test step to verify connections:

- name: Test connectivity
  run: |
    ping -c 1 example.com || echo "Ping failed"
    curl -I https://example.com || echo "HTTPS failed"
    nslookup example.com || echo "DNS failed"

Known Issues​

GitHub Actions Checkout​

The actions/checkout action itself makes network calls to GitHub. If Bullfrog is truly first, these should be automatically allowed. If you see issues:

allowed-domains: |
  github.com
  *.github.com

npm/yarn Network Issues​

Package managers can be sensitive to network interruptions:

allowed-domains: |
  registry.npmjs.org
  *.npmjs.org
  *.yarnpkg.com

Docker Rate Limits​

Docker Hub rate limits can cause failures. These aren't Bullfrog issues but can appear similar:

Error: toomanyrequests: Too Many Requests

Solution: Authenticate to Docker Hub or use GitHub Container Registry.

Best Practices to Avoid Issues​

  1. Always start with audit mode
  2. Test in non-production workflows first
  3. Document your allow list with comments
  4. Keep Bullfrog updated to the latest version
  5. Review workflow summaries after every change
  6. Use specific domains instead of broad wildcards when possible
  7. Disable sudo unless absolutely necessary
  8. Pin to commit SHA for reproducible builds
