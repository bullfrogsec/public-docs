Run Bullfrog on a host with Tailscale

Add the Tailscale integration to a policy so tailscaled can coordinate, relay and reach other devices, while every connection your workloads make through the tunnel is still judged by the policy.

Without it, an egress policy treats tailscaled like any other process. Almost everything it sends goes to IP addresses it never looked up, so audit mode raises a Would block row for each relay, STUN server and peer, and block mode keeps the device offline.

Before you begin​

  • Admin access to the organization in Bullfrog. See Roles and permissions.
  • A workspace with Tailscale installed and logged in. See Install Bullfrog on a workspace.
  • An egress policy for the workspace's tag. See Enforce an egress policy across your organization.

Step 1: Check that tailscaled runs in kernel mode​

Bullfrog recognizes tailscaled's traffic by the firewall mark tailscaled sets in its default kernel mode. In userspace-networking mode tailscaled sets no mark, and its traffic is refused like any other process's.

On the workspace, run:

ip link show tailscale0 && ip rule | grep 0x80000

The command prints the tailscale0 interface and at least one rule naming fwmark 0x80000/0xff0000. If it prints Device "tailscale0" does not exist, tailscaled runs in userspace-networking mode: remove --tun=userspace-networking from its flags and restart it before you continue.

Step 2: Add the Tailscale integration​

  1. In the left navigation, select Policies.
  2. Open the policy for the workspace's tag.
  3. On the Destinations tab, select + Add integration, then select Tailscale.
  4. Leave Allow package updates on if the workspace updates Tailscale with apt or tailscale update.

For a new policy, select + New policy, select Tailscale in the catalog, then select Continue.

The integration turns on Tailscale transport on the Settings tab, shown as turned on by the Tailscale integration. It also ignores tailscaled's coordination and log servers rather than allowing them: tailscaled reaches them without an allowlist entry, and allowing the log servers would let any process on the workspace write to an intake shared by every Tailscale account.

Step 3: Allow the devices your workloads reach​

Tailscale transport covers tailscaled's own traffic, not what your workloads send through the tunnel. Add the devices they need on the Destinations tab:

  • By MagicDNS name: enter *.<your-tailnet>.ts.net, using your tailnet's DNS name from the Tailscale admin console. This also stops lookups that try your tailnet's search domain, such as api.github.com.<your-tailnet>.ts.net, from being raised.
  • By address: enter 100.64.0.0/10 and fd7a:115c:a1e0::/48 for every device, or the addresses of the devices you need.

Never enter *.ts.net. It matches the public Funnel hostnames of every tailnet, not only yours.

Step 4: Save and verify​

  1. Review the change on the Review tab, then save.
  2. Wait for the workspace to pick up the policy, then run tailscale status on it. The workspace's own line does not say offline.
  3. On the workspace's Activity tab, search for tailscaled. No connection shows Would block or Blocked.

What is still yours to control​

  • tailscale funnel and tailscale serve publish from the workspace through Tailscale's relays, inside the traffic Tailscale transport lets through. Whoever can run the tailscale command as root or as its operator user controls them. Leave the operator user unset, or set it to a user your workloads don't run as.
  • A process with CAP_NET_ADMIN can set any firewall mark, as it can change any firewall rule. Withhold root and sudo from the workloads you want held to the policy. See Sudo policy.
